## 🔴 Подтверждённые баги

### При включённом VPN не открываются сетевые папки домена (`\\bshk`) — высокий приоритет
- **Симптом.** `\\bshk` → «Данная учётная запись не может быть использована для входа в сеть с
  этой станции». С выключенным SimpleRay открывается. Компьютер не в домене, вход учёткой
  `o.baskov@HK.LOCAL`.
- **Доказано (2026-11-13, VPN включён):** SRV-записи контроллера домена
  (`_kerberos._tcp.hk.local`, `_ldap._tcp.dc._msdcs.hk.local`) → «нет такого имени»; DNS к офисному
  серверу `172.17.0.2:53` заблокирован (таймаут), при этом Kerberos `:88`, LDAP `:389` и SMB `:445`
  доступны. Имена `bshk`, `fs`, `hkad01/02` отвечают только из кэша DNS (TTL 0) — со временем
  перестанут резолвиться совсем.
- **Цепочка.** sing-box с `strict_route` закрывает DNS (порт 53) на всех интерфейсах, кроме
  туннеля → все запросы идут в sing-box → `hk.local` ни в одном правиле → уходит в Cloudflare через
  туннель → «нет такого имени» → Windows не находит контроллер домена → Kerberos невозможен →
  откат на NTLM → для этой учётки вход по NTLM с этой станции запрещён → ошибка.
- **Исправление:** split-DNS (см. раздел решений) — sing-box сам спрашивает офисный DNS для
  внутреннего домена.

## ℹ️ Разобрано — не баги SimpleRay

- **«Пропал интернет на проводе» (2026-09-14).** Блок устройства на MikroTik по MAC/IP: при
  *выключенном* SimpleRay шлюз пинговался, LAN и DNS работали, а в интернет `tracert` умирал на
  первом хопе. Со сменой MAC интернет вернулся. Блок на роутере ещё надо снять.
- **`curl` при мёртвом сервере.** `google.com → Resolving timed out` — это proxy-домен, его DNS
  идёт через мёртвый туннель; разовый сброс на `yandex.ru` — шум. Браузер (реальный трафик)
  прямые сайты открывает.
- **`ping` в интернет через туннель не отвечает.** sing-box не проксирует ICMP — проверять по TCP
  (`Test-NetConnection хост -Port 443`) или браузером.
- **Восстановление после краша с kill-switch требует прав администратора** (или перезагрузки) —
  так задумано: фильтры переживают краш, чтобы не было утечки.

## 📋 Решения и бэклог

### T4 / block-53 — пересмотрено, решение за архитектурой
- **Что такое T4.** Когда туннель мёртв, Windows отправляет DNS-запросы на резолвер LAN
  (у тебя `172.17.0.2–4` — корпоративный DNS домена `hk.local`), и kill-switch их пропускает,
  потому что LAN разрешён. Окно — пока туннель не поднимется.
- **Почему block-53 «в лоб» нельзя.** План был заблокировать исходящий порт 53 мимо туннеля. Но
  тогда при *работающем* VPN Windows перестанет достучаться до корпоративного DNS: внутренние
  имена (`*.hk.local`, контроллер домена — Kerberos, политики, общие папки) уйдут в sing-box, а он
  отправит их в Cloudflare через туннель и получит «нет такого имени». Для бизнес-продукта
  (целевой сегмент — компании на 1000–1500 человек) это регресс хуже, чем закрываемая утечка.
- **Split-DNS нужен уже сейчас, не только ради block-53:** без него при VPN не работает вход в
  домен (см. «Подтверждённые баги»).
- **Правильный путь — split-DNS.** При подключении брать DNS-суффикс и DNS-серверы физического
  адаптера (`hk.local → 172.17.0.2`) и добавлять в sing-box правило «этот суффикс → корпоративный
  резолвер напрямую». Внутренние имена тогда резолвит sing-box (он разрешён в kill-switch), и уже
  можно включать строгий DNS (block-53) без поломки домена.
- **Статус:** не реализуется, пока не принято архитектурное решение (Claude + opponent).
