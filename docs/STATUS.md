## 🔴 Подтверждённые баги

### При включённом VPN не открываются сетевые папки домена (`\\bshk`) — исправлено в 0.3.10 (split-DNS), ждёт живой проверки (п. 5)
- **Симптом.** `\\bshk` → «Данная учётная запись не может быть использована для входа в сеть с
  этой станции». С выключенным SimpleRay открывается. Компьютер не в домене, вход учёткой
  `o.baskov@HK.LOCAL`.
- **Доказано (2026-11-13, VPN включён):** SRV-записи контроллера домена
  (`_kerberos._tcp.hk.local`, `_ldap._tcp.dc._msdcs.hk.local`) → «нет такого имени»; DNS к офисному
  серверу `172.17.0.2:53` заблокирован (таймаут), при этом Kerberos `:88`, LDAP `:389` и SMB `:445`
  доступны. Имена `bshk`, `fs`, `hkad01/02` отвечают только из кэша DNS (TTL 0) — со временем
  перестанут резолвиться совсем.
- **Цепочка.** sing-box с `strict_route` закрывает DNS (порт 53) на всех интерфейсах, кроме
  туннеля → все запросы идут в sing-box → `hk.local` ни в одном правиле → уходит в Cloudflare через
  туннель → «нет такого имени» → Windows не находит контроллер домена → Kerberos невозможен →
  откат на NTLM → для этой учётки вход по NTLM с этой станции запрещён → ошибка.
- **Исправление:** split-DNS (см. раздел решений) — sing-box сам спрашивает офисный DNS для
  внутреннего домена.

### 0.3.10 падает при запуске (`Hyperlink.NavigateUri`) — исправлено в 0.3.11, ждёт живой проверки (п. 9)
- **Причина.** В панели «О программе» у ссылки было `NavigateUri="{x:Static ...SourceUrl}"`:
  `x:Static` подставляет строку, а свойству нужен `Uri`, и разметка главного окна падает при
  загрузке. Ни один тест не создавал окно, поэтому ошибка ушла в релиз.
- **Исправление.** Ссылка открывается через `Click`. Новый `WindowXamlLoadTests` разбирает
  разметку всех 5 окон через `XamlReader`, без кода окна и без данных пользователя. «Зубы»
  проверены: со старой ссылкой тест падает ровно с этой ошибкой.

### После обновления программа «висит» без окна — исправлено в 0.3.11, ждёт живой проверки (п. 9)
- **Причина.** Старая копия (0.3.9, запущена от администратора, свёрнута в трей) продолжала
  работать. Новая находила её и молча выходила; окно спрятанной копии найти нельзя
  (`MainWindowHandle == 0`), а вывести окно процесса с более высоким уровнем целостности мешает UIPI.
- **Исправление.** Именованное событие `Local\SimpleRay.ShowWindow` с меткой Medium integrity:
  второй запуск сигналит — работающая копия показывает окно из трея. Если сигнал не дошёл —
  сообщение «уже запущен» с подсказкой про «Выход». Старые копии апдейтера в TEMP чистятся.

## ℹ️ Разобрано — не баги SimpleRay

- **«Пропал интернет на проводе» (2026-09-14).** Блок устройства на MikroTik по MAC/IP: при
  *выключенном* SimpleRay шлюз пинговался, LAN и DNS работали, а в интернет `tracert` умирал на
  первом хопе. Со сменой MAC интернет вернулся. Блок на роутере ещё надо снять.
- **`curl` при мёртвом сервере.** `google.com → Resolving timed out` — это proxy-домен, его DNS
  идёт через мёртвый туннель; разовый сброс на `yandex.ru` — шум. Браузер (реальный трафик)
  прямые сайты открывает.
- **`ping` в интернет через туннель не отвечает.** sing-box не проксирует ICMP — проверять по TCP
  (`Test-NetConnection хост -Port 443`) или браузером.
- **Восстановление после краша с kill-switch требует прав администратора** (или перезагрузки) —
  так задумано: фильтры переживают краш, чтобы не было утечки.

## 📋 Решения и бэклог

### T4 / block-53 — пересмотрено, решение за архитектурой
- **Что такое T4.** Когда туннель мёртв, Windows отправляет DNS-запросы на резолвер LAN
  (у тебя `172.17.0.2–4` — корпоративный DNS домена `hk.local`), и kill-switch их пропускает,
  потому что LAN разрешён. Окно — пока туннель не поднимется.
- **Почему block-53 «в лоб» нельзя.** План был заблокировать исходящий порт 53 мимо туннеля. Но
  тогда при *работающем* VPN Windows перестанет достучаться до корпоративного DNS: внутренние
  имена (`*.hk.local`, контроллер домена — Kerberos, политики, общие папки) уйдут в sing-box, а он
  отправит их в Cloudflare через туннель и получит «нет такого имени». Для бизнес-продукта
  (целевой сегмент — компании на 1000–1500 человек) это регресс хуже, чем закрываемая утечка.
- **Split-DNS нужен уже сейчас, не только ради block-53:** без него при VPN не работает вход в
  домен (см. «Подтверждённые баги»).
- **Правильный путь — split-DNS.** При подключении брать DNS-суффикс и DNS-серверы физического
  адаптера (`hk.local → 172.17.0.2`) и добавлять в sing-box правило «этот суффикс → корпоративный
  резолвер напрямую». Внутренние имена тогда резолвит sing-box (он разрешён в kill-switch), и уже
  можно включать строгий DNS (block-53) без поломки домена.
- **Статус:** не реализуется, пока не принято архитектурное решение (Claude + opponent).

### DNS для прямого трафика: автопереключения пока нет
- В конфиге один резолвер для прямого трафика. Если он недоступен, прямые сайты (российские и
  «Прямые домены») не открываются, пока не выбрать другой вручную; на трафик через VPN это не влияет.
- План: при подключении быстро проверить выбранный; не отвечает — на эту сессию взять самый быстрый
  доступный и написать об этом в статусе (выбор пользователя не меняется).

### Автозапуск с Windows — разбор оппонента (2026-11-16): в исходном виде негодно
Пользователь выбирает один из двух вариантов: А — задача Планировщика при входе, Б — служба
Windows. Утверждения о коде проверены по исходникам.

**Блокеры, общие для А и Б.**
- **Установка в профиль пользователя.** Сейчас программа ставится в
  `%LocalAppData%\Programs\SimpleRay` (`installer.iss`: `PrivilegesRequired=lowest`), и её файлы
  может менять процесс без прав. Если такой exe запускать с наивысшими правами без UAC (А) или от
  SYSTEM (Б), это готовый обход UAC или повышение до SYSTEM: зловред подменяет `sing-box.exe` и
  ждёт следующего запуска. → Автозапуск включается только для машинной установки в
  `Program Files`. Portable-версия и установка «для себя» — без автозапуска.
- **Окно при старте сносит чужой движок.** До создания окна оно вызывает
  `EngineOrphans.KillStale` и `WfpKillSwitch.CleanupLeftovers`. Если работает служба (или вторая
  копия), открытие окна убьёт её sing-box и снимет kill-switch. → Нужен один владелец TUN и WFP на
  машину с атомарным захватом владения. В режиме службы окно ничего не чистит.

**Только А.**
- **Значения Планировщика по умолчанию.** Задача не стартует на батарее, останавливается при
  отключении питания и завершается через 72 часа. → Явно отключить батарейные флаги, задать
  `ExecutionTimeLimit=PT0S` и политику экземпляров. Проверять фактический XML задачи, а не код
  возврата `schtasks`.
- **Чужая учётная запись — это чужой профиль.** Стандартный пользователь, который вводит в UAC
  данные администратора, получает процесс от имени администратора. Профили, зашифрованные DPAPI
  CurrentUser, тот прочитать не сможет. → В А только текущий пользователь, его SID фиксируется до
  повышения. Для стандартных пользователей в компаниях подходит только Б.
- **Имя задачи общее для машины.** → Своя задача на каждый SID и одну установку. Удаление — через
  повышенный helper.

**Только Б.**
- **Отдельный процесс службы.** Нужен `SimpleRay.Service.exe` без WPF, в защищённом машинном
  каталоге. Изменяемые данные лежат в `ProgramData` с ACL.
- **IPC — типизированные параметры, а не JSON.** Служба сама выбирает пути и генерирует конфиг.
  Теги rule-set принимаются только из своего каталога: сейчас
  `Path.Combine(RuleSetDirectory, tag + ".srs")` пропустит `../`.
- **Канал.** Явная DACL без `FILE_CREATE_PIPE_INSTANCE` для клиентов, без удалённых подключений.
  Права разделены: статус, управление, политика. Лимиты на размер и число сообщений.
- **Обновление.** Привилегированная сторона сама перепроверяет подпись пакета и ставит его в
  фиксированные каталоги. Успех подтверждается handshake со службой.
- **Защита с начала загрузки не обещается.** WFP-фильтры не переживают перезагрузку. Первая версия
  Б не подключается до входа пользователя.

**Настройки разделить на три.** «Запускать окно при входе», «Режим VPN: обычный или служба» и
«Когда подключаться». В диалоге для А подпись — «в чьём сеансе запускать», для Б — «кому разрешено
управлять».

**Порядок работ (предложение).**
1. Общая основа: машинная установка в `Program Files` (опция установщика), единый владелец
   TUN/WFP, окно не чистит чужое.
2. А для текущего пользователя с исправленными параметрами задачи.
3. Б — минимальный сквозной сценарий: защищённая установка, непривилегированное окно,
   подключение, восстановление, обновление.
4. Подключение до входа в систему — отдельным этапом, если оно нужно.

### Ревью качества кода (2026-11-23, GPT + проверка Claude по коду)
Общая оценка: «рабочее с оговорками». Основа разумная: отдельный `ConnectionController`,
подменяемый `IProcessLauncher`, генератор разбит на тематические методы. Слабые места — обработка
отказов и владение ресурсами. Все находки ниже сверены с кодом.

**Надёжность (делать первыми):**
1. **Откат обновления** (`UpdateService.cs:187–198`). Если новый exe не запустился (`TryStart` →
   null), отката нет, а резервная копия всё равно удаляется. Ошибка посреди `CopyOver` оставляет
   смесь файлов старой и новой версии. Тест `RunApplyUpdate_CopiesStagingOverTarget_PreservingExtras`
   закрепляет эту ветку.
2. **Гонка при старте движка** (`SingBoxEngine.cs:133–143`). Между проверкой `HasExited` и
   подпиской на `Exited` процесс может завершиться. Тогда показывается «Подключено» при мёртвом
   sing-box, или `Running` перезаписывает `Faulted`.
3. **Исключение в `process.Start()`** (`SingBoxEngine.cs:115`): остаётся `Starting` и ссылка на
   процесс. При отмене `sing-box check` (`RunOnceAsync`) процесс не убивается.
4. **WFP `Disengage`** (`WfpKillSwitch.cs:113–120, 297–311`). Коды возврата `Fwpm*DeleteByKey0`
   игнорируются, а `IsEngaged = false` ставится всегда. Неудачное удаление block-all = сети нет,
   а программа считает защиту снятой.
5. **Job Object** (`EngineProcess.cs:111`): результат `AssignProcessToJobObject` не проверяется,
   хотя комментарий обещает гарантию.

**Структура и переиспользуемость:**
6. **`MainViewModel` (1441 строка).** Главная беда — не длина, а побочные эффекты конструктора:
   создаёт хранилища, читает данные пользователя, запускает таймеры, подписывается на глобальное
   событие, а `ShutdownAsync` их не снимает. Из-за этого VM нельзя протестировать. План по шагам,
   каждый шаг — отдельный коммит:
   1. конструктор с зависимостями (XAML не меняется);
   2. явные Start и Shutdown;
   3. обновления — в отдельный компонент;
   4. профили, подписки и импорт;
   5. замеры DNS и задержек с отменой.

   После каждого шага — тест привязок на настоящей VM.
7. **Дублирование base64url** (`ShareLinkParser.cs:473`, `SubscriptionParser.cs:194`) → общий
   декодер; контракты ошибок у двух парсеров оставить разными.
8. **Инфраструктура.** Добавить `Directory.Build.props` (Nullable, `AnalysisLevel`,
   `EnforceCodeStyleInBuild`, потом `TreatWarningsAsErrors`) и `.editorconfig` (UTF-8, 4
   пробела, CA2000/CA2012 = warning, `*.g.cs` = generated). Встроенные анализаторы SDK уже
   работают — нужна явная политика, а не новые пакеты.
9. **Пустые `catch`** — 35 шт. Большинство — осознанная очистка. Но молча глотаются ошибки
   отката обновления (`UpdateService.cs:193–194`) и удаления WFP (п. 4) → логировать.
