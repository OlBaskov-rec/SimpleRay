# Проверка опции «Включить IPv6»

## Контекст (почему IPv6 по умолчанию выключен)

На машине пользователя (сеть без нативного IPv6) прямые соединения по IPv6 **сбрасывались**:
подтверждено `curl -4` (работает) против `curl -6` (reset) для `ya.ru`, `360.yandex.ru`,
`mail.ru`. Причина: у сайтов есть AAAA-записи, клиент лезет по IPv6 первым, а у прямого
outbound нет физического IPv6-пути → сброс. Через VPN IPv6 работает (инкапсулируется в туннель).

Поэтому по умолчанию клиент работает **IPv4-only**:
- `dns.strategy = "ipv4_only"` (отдаём только A-записи);
- у TUN нет IPv6-адреса (auto_route не добавляет IPv6-маршрут по умолчанию).

Настройка **«Включить IPv6»** (Маршрутизация, по умолчанию выкл., с подсказкой) возвращает
dual-stack: `dns.strategy = "prefer_ipv4"` и IPv6-адрес на TUN.

## Когда и как тестировать (будущий тест)

Нужна сеть с **рабочим нативным IPv6** (проверить: `Test-NetConnection -6 ipv6.google.com`
или `curl -6 https://ipv6.google.com` **без** VPN должен отвечать).

1. Свежая сборка, подключиться (Режим «По правилам»).
2. Галка **«Включить IPv6»** — выкл. → `curl -6 https://ipv6.google.com` может не работать
   (это ожидаемо на IPv4-only): убеждаемся, что обычный сёрфинг по IPv4 в порядке.
3. Включить галку → переподключиться.
4. Проверить:
   - зарубежный IPv6 через туннель: `curl -6 -m 8 https://ipv6.google.com` → отвечает;
   - российский IPv6 напрямую (если у сети есть IPv6): `curl -6 -m 8 https://ya.ru` → отвечает,
     **без** сброса;
   - обычные IPv4-сайты не сломались.
5. Выключить галку → переподключиться → снова IPv4-only, всё работает.

## Ожидание

- На сети **без** IPv6: галку не трогать (IPv4-only — правильный дефолт, всё работает).
- На сети **с** IPv6: с включённой галкой IPv6-сайты доступны и напрямую, и через туннель,
  без сбросов.
